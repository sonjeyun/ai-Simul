# Mini NPU 시뮬레이터

## 실행 방법
```bash
python main.py
```
- 실행 후 `1`(사용자 입력 3×3) 또는 `2`(data.json 분석)를 선택합니다. 1, 2 외의 입력은 안내 후 다시 묻습니다.
- `data.json`은 `main.py`와 같은 폴더에 둡니다.
- Python 3.8+, 표준 라이브러리(`json`, `math`, `re`, `time`, `os`, `sys`)만 사용합니다.

### 모드 1 출력 예시 (필터 A = 십자가, 필터 B = X, 패턴 = X)
```
필터 A, B 저장 완료
[저장 확인] 필터 A
  0 1 0 / 1 1 1 / 0 1 0
...
--- 결과 ---
A 점수: 1  (평균 0.001390 ms)
B 점수: 5  (평균 0.000700 ms)
판정: B
```
점수(MAC), 연산 시간(ms), 판정(A / B / 판정 불가)이 출력되고, 이어서 3×3 성능 분석 표가 나옵니다.

### 모드 1 입력 오류 예시
```
  1행: 0 1
입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요.
  1행: 1 a 1
입력 형식 오류: 숫자만 입력할 수 있습니다.
```
오류가 나면 해당 행렬(필터 또는 패턴)을 처음부터 다시 입력받습니다.

## 구현 요약
- **데이터 구조**: `Matrix` 클래스가 n×n 2차원 배열을 저장하고 `set(r, c, v)` / `get(r, c)`로 특정 위치를 쓰고 읽습니다. 모드 1 입력과 모드 2 필터·패턴 모두 이 클래스에 담아 처리합니다(3×3 ~ 25×25).
- **MAC 연산**: `mac(pattern, filter)`가 이중 반복문으로 같은 위치의 값을 곱해 누적합니다(외부 라이브러리 없음). 반환값은 합계 `float` 하나이며, **점수가 높을수록 패턴이 해당 필터와 더 유사**하다는 뜻입니다.
- **라벨 정규화**: 아래 표처럼 표기가 다른 라벨을 표준 라벨 `Cross` / `X`로 통일하고, 모든 출력과 PASS/FAIL 비교는 표준 라벨 기준으로 합니다.

  | 입력 위치 | 원본 값 | 표준 라벨 |
  |---|---|---|
  | expected | `+` | Cross |
  | expected | `x` | X |
  | filter 키 | `cross` | Cross |
  | filter 키 | `x` | X |

  대소문자와 앞뒤 공백은 무시하며(`Cross`, `X`, ` x `도 허용), 그 외 값은 오류가 되어 해당 케이스만 FAIL 처리됩니다.
- **정규화를 함수(`normalize_label`)로 분리한 이유**: expected와 필터 키 두 곳에서 같은 규칙을 쓰므로 한 곳에서 관리하면 규칙이 어긋날 일이 없고(재사용성), 입력 → 표준 라벨 변환만 따로 테스트할 수 있습니다(테스트 용이성).
- **동점 처리**: `abs(score_a - score_b) < 1e-9`이면 동점으로 보고 `UNDECIDED`(모드 1은 "판정 불가")로 처리합니다. 1e-9를 고른 이유: 점수는 최대 625개 항의 합이라 double 누적 오차는 이론상 최악이어도 1e-11 수준이고(이번 데이터에서 관측된 최대 오차는 2.7e-15), 이번 데이터에서 실제로 구분되는 점수 차이는 8.8 이상입니다. 그래서 1e-9는 오차는 동점으로 묶고 실제 차이는 놓치지 않는 값입니다.
- **검증**: 모드 1은 행/열 개수·숫자 파싱 오류(`nan`, `inf` 포함) 시 안내 후 재입력합니다. 모드 2는 스키마·크기 불일치를 케이스 단위 FAIL로 기록하고 프로그램은 계속 진행합니다. `meta` 등 추가 키는 무시합니다.
- **보너스**: 1차원 배열 기반 `mac_flat()`과 2D/1D 성능 비교, `make_cross()` / `make_x()` 패턴 생성기(성능 분석에서 사용).

### data.json 처리 흐름 (키에서 N 추출 → 필터 선택 → 크기 검증)
1. `filters`의 키 `size_5`, `size_13`, `size_25`에서 정규식 `size_(\d+)`로 N을 읽어 `{N: {Cross: 필터, X: 필터}}` 형태로 보관합니다. 필터 안의 키(`cross`, `x`)는 이때 정규화합니다.
2. 각 패턴 키(예: `size_13_2`)에서 정규식 `size_(\d+)_(\d+)`로 N=13을 추출합니다.
3. N=13에 해당하는 `size_13` 필터를 선택합니다. 없거나 잘못된 필터면 `필터 오류`로 FAIL 처리합니다.
4. 패턴 `input`이 13×13인지 검증합니다. 아니면 `크기 불일치: 키는 13x13인데 input 크기가 다름`처럼 사유를 남기고 FAIL 처리합니다.
5. 통과하면 Cross/X 두 필터와 MAC을 계산해 판정하고, expected(정규화된 값)와 비교해 PASS/FAIL을 출력합니다.

### 콘솔 출력 예시 (모드 2)
```
size_5_1: Cross=0.9, X=0.9 -> UNDECIDED (expected X) FAIL
size_5_2: Cross=8.9, X=0.1 -> Cross (expected Cross) PASS
...
--- 결과 요약 ---
전체 테스트: 6
통과: 3
실패: 3
실패 케이스:
  - size_5_1: 동점(UNDECIDED)
  - size_13_2: 동점(UNDECIDED)
  - size_25_1: 동점(UNDECIDED)
```
동점 출력은 모드별로 다릅니다. 모드 1은 `판정: 판정 불가`, 모드 2는 `-> UNDECIDED ... FAIL`로 표시됩니다.

### 라벨을 새로 추가하려면
1. `normalize_label()`에 새 표기를 표준 라벨로 매핑하는 조건을 추가합니다.
2. data.json의 각 `size_N` 필터에 새 라벨 필터를 넣고, `load_filters()`의 "Cross/X 모두 필요" 검사를 새 라벨까지 확장합니다.
3. `judge()`는 현재 두 점수만 비교하므로, 라벨이 셋 이상이면 최고 점수 라벨을 고르고 상위 점수가 epsilon 이내로 겹치면 UNDECIDED로 처리하도록 바꿉니다.
4. 새 라벨 케이스를 data.json에 추가해 PASS/FAIL 출력과 요약이 맞는지 확인합니다.

| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |

### 성능 표 (각 크기 10회 반복 평균)

| 크기(N×N) | 평균 시간(ms) | 1D 평균(ms) | 연산 횟수(N²) |
|---|---|---|---|
| 3×3 | 0.000610 | 0.000410 | 9 |
| 5×5 | 0.001070 | 0.000620 | 25 |
| 13×13 | 0.005200 | 0.003510 | 169 |
| 25×25 | 0.017720 | 0.013660 | 625 |

(Windows PowerShell에서 `python main.py` 모드 2 실행으로 측정한 값입니다. 시간은 실행 환경에 따라 달라집니다.)

**측정 방법**: `time.perf_counter()`를 `mac()` 호출 직전과 직후에만 찍고, 같은 입력으로 10회 호출한 총 시간을 10으로 나눠 ms로 환산합니다. 입력, 출력(print), 파일 읽기, 1차원 배열 변환은 측정 구간 밖이라 I/O 시간이 포함되지 않습니다. 워밍업 호출은 따로 두지 않았고 첫 호출도 평균에 포함됩니다. 2D와 1D는 동일한 입력과 동일한 반복 횟수로 비교했습니다.

**이론(N²)과 측정값 비교 (3×3 대비 배율)**

| 크기 | 연산 횟수 배율 | 측정 시간 배율 |
|---|---|---|
| 5×5 | 2.8배 | 1.8배 |
| 13×13 | 18.8배 | 8.5배 |
| 25×25 | 69.4배 | 29.1배 |

### 실패 원인 분석
1. 실패 3건(size_5_1, size_13_2, size_25_1)은 모두 **두 필터의 점수가 수학적으로 같아서** 생긴 동점입니다. 라벨/스키마 문제도, 크기 불일치도 아닙니다(분류: 수치 비교 문제).
2. MAC 점수는 높을수록 패턴이 그 필터와 더 닮았다는 뜻이라 두 점수가 같으면 어느 쪽이 더 닮았다고 말할 수 없습니다. 이 데이터는 필터 가중치가 0.9, 0.1, 0.3, 4.9 같은 소수 값이라 점수가 우연히 같아지게 구성되어 있습니다. 예: size_5_1은 Cross 필터와 겹치는 칸이 중앙 하나뿐이라 0.9, X 필터는 0.1이 9칸이라 0.9입니다.
3. 부동소수점 오차 때문에 실제 계산값은 완전히 같지 않습니다. size_5_1은 0.9 vs 0.8999999999999999(차이 1.1e-16), size_13_2는 7.499999999999997 vs 7.5(차이 2.7e-15), size_25_1은 4.9 vs 4.899999999999999(차이 1.8e-15)입니다.
4. epsilon 없이 `>`로 비교하면 이 미세한 차이가 승패를 가릅니다. 세 케이스 모두 expected와 반대로 판정되어 근거 없는 오답이 됩니다.
5. epsilon(1e-9) 정책을 쓰면 세 케이스가 모두 올바르게 UNDECIDED(동점)로 판정됩니다. 다만 요구사항상 UNDECIDED는 expected(Cross/X)와 일치하지 않으므로 PASS/FAIL 비교에서는 FAIL로 집계됩니다.
6. 따라서 이 FAIL은 로직 버그가 아니라 "구분할 수 없는 입력을 구분할 수 없다고 판정한 결과"입니다. 점수를 억지로 바꿔 PASS를 만들지 않았습니다.
7. 개선 방향: 동점 시 별도 규칙(예: 보조 지표나 정규화된 점수 비교)을 두거나, 데이터의 필터 가중치를 조정하면 구분 가능해집니다. 이는 정책 변경이므로 이번 구현에는 넣지 않았습니다.
8. 나머지 3건은 정규화(`+`→Cross, `x`→X)가 정상 적용되어 PASS입니다. 정규화가 없었다면 `+`와 `Cross`가 달라 정답도 FAIL로 처리되었을 것입니다.

### 시간 복잡도 분석
9. N×N 패턴의 MAC은 곱셈·덧셈을 N²번 수행하므로 시간 복잡도는 **O(N²)**입니다.
10. 3×3(9회) → 25×25(625회)로 연산 횟수가 약 69배 늘 때 측정 시간은 약 29배 늘었습니다. 작은 크기에서는 함수 호출·타이머 고정 오버헤드가 커서 배율이 이론보다 작게 보입니다.
11. 13×13 → 25×25는 연산 횟수가 약 3.7배, 시간이 약 3.4배로 N²에 거의 비례합니다. 크기가 클수록 고정 오버헤드의 비중이 줄어 이론값에 가까워집니다.
12. 1차원 배열 방식은 인덱스 접근이 줄어 2D보다 약간 빠르지만, 복잡도는 동일하게 O(N²)입니다.

### CPU와 NPU, 대규모로 갈 때의 병목
13. CPU는 명령을 순서대로 처리하는 직렬 방식에 최적화되어 있어, 이 시뮬레이터처럼 N² 번의 곱셈·덧셈을 하나씩 반복해야 합니다. NPU는 서로 독립적인 곱셈을 수천 개씩 동시에 처리(병렬화)해 같은 작업의 시간을 줄입니다.
14. 이 시뮬레이터(순수 Python)에서는 원소 하나를 처리할 때마다 인터프리터 오버헤드가 붙는 것이 주된 비용입니다. 위의 2D/1D 비교처럼 접근 방식을 단순하게 만드는 것만으로도 시간이 줄었습니다.
15. 필터가 수백×수백 크기로 커지고 수천 개가 되면 연산량과 함께 데이터를 옮기는 비용이 중요해집니다. 일반적으로 실제 하드웨어에서는 메모리 대역폭(데이터 이동)과 병렬 처리 결과를 모을 때의 동기화가 병목이 되기 쉽습니다(이번 과제에서 직접 측정한 내용은 아니며 일반적인 설명입니다).
16. 따라서 대규모에 대응할 때의 우선순위는 ① 메모리 접근 패턴 단순화(연속된 1차원 배열 등), ② 독립적인 MAC의 병렬화, ③ 병렬 결과를 합치는 동기화 비용 줄이기 순서로 생각할 수 있습니다.
